# ASTRA 전용 구현 프롬프트 — CSI RX/TX 바탕화면 수집 실행기

아래 내용을 그대로 ASTRA 모델에 입력한다.

---

당신은 이 저장소를 직접 수정하고 검증하는 시니어 Linux/Python 엔지니어다. 설명이나 설계안만 제시하지 말고, 기존 성공 수집 파이프라인을 보존하면서 RX PC와 TX PC에서 사용할 바탕화면 실행 버튼과 대화형 터미널 실행기를 실제로 구현하라.

## 2. 성공 기준으로 사용할 환경

사용자에게 보이는 핫스팟 이름은 **`김민혁 핫스팟`**으로 표시하고, 실제 Wi-Fi SSID는 **`Minhyuck S24+`**로 관리하라.

김민혁 핫스팟 프로필의 기준값은 다음과 같다.

- 표시 이름: `김민혁 핫스팟`
- 실제 SSID: `Minhyuck S24+`
- AP 종류: 휴대폰 핫스팟/AP
- Wi-Fi 대역: 2.4 GHz
- 성공 당시 주파수/채널: 2437 MHz / 채널 6
- RX 무선 인터페이스 기준값: `wlp4s0`
- RX 무선 MAC 기준값: `00:16:ea:ed:a9:80`
- RX 커널: `4.15.0-213-generic`
- CSI 드라이버: CSI Tool용 수정 `iwlwifi`
- `connector_log`: `1`
- 데이터 트래픽: UDP, 포트 `5005`, 초당 100패킷, 페이로드 512 bytes
- TX 송신 시간: RX 수집 시간보다 10초 길게
- 카메라 기준: `/dev/video0`, 640x480, 10 FPS, 미리보기와 WebM 녹화 동시 수행
- 활동 기본값: `natural`
- 안테나 거치대 기본값: `3d_printed_v1`
- 수집 목적 기본값: `training`

중요: 성공 당시 BSSID `be:93:07:3c:38:15`, RX IP `10.175.218.22`, TX IP `10.175.218.104`는 참고 정보일 뿐이다. 핫스팟 재시작/DHCP 갱신 때 바뀌므로 코드에 고정하지 말고 실행 시 현재 값을 탐지하라. Wi-Fi 비밀번호는 저장소나 로그에 하드코딩하거나 출력하지 말라. 연결돼 있지 않다면 사용자가 OS의 NetworkManager에서 먼저 연결하도록 명확히 안내하라.

## 3. 만들어야 할 결과물

이름은 저장소 관례에 맞게 조정할 수 있지만 역할은 모두 충족해야 한다.

1. RX용 대화형 실행기
   - 예: `tools/csi_capture_rx_launcher.py`
2. TX용 대화형 실행기
   - 예: `tools/csi_capture_tx_launcher.py`
3. RX/TX가 공유하는 제어 프로토콜 또는 공통 유틸리티
4. RX 바탕화면용 `.desktop` 실행 버튼
5. TX 바탕화면용 `.desktop` 실행 버튼
6. 현재 PC에 역할별 버튼을 설치하는 안전하고 재실행 가능한 설치 스크립트
7. 사용법/복사 방법/장애 대응을 설명하는 짧은 문서
8. 실제 네트워크·CSI 로거·카메라 없이도 상태 전이와 입력 검증을 확인할 자동 테스트

`.desktop` 파일은 `Terminal=true`로 터미널을 열어야 하며, 사용자가 아이콘을 더블 클릭했을 때 프로젝트 루트와 무관한 현재 디렉터리에서도 정상 실행돼야 한다. RX 프로젝트는 현재 `~/바탕화면/project`, 성공 당시 TX 명령의 프로젝트는 `~/바탕화면/projects`였으므로 경로를 맹목적으로 한쪽에 고정하지 말라. 설치 시 실제 절대 경로를 기록하거나 실행기 자신의 위치에서 프로젝트 루트를 안전하게 계산하라. 한국어 Desktop 폴더와 영문 `Desktop` 환경을 모두 고려하되, 존재하는 사용자 바탕화면만 대상으로 하라. 시스템 전체 설치나 root 소유 파일 생성은 피하라.

## 4. 실행 시 사용자 질문

RX 터미널에서 순서대로 다음을 묻고 입력을 검증하라.

1. 수집 인원 수
   - 양의 정수만 허용한다.
   - 결과 저장 루트는 기존 형식에 맞춰 `data/<N>_people`로 계산한다.
2. 연결한 핫스팟 소유자/프로필
   - 기본 선택은 `김민혁 핫스팟 (SSID: Minhyuck S24+)`이다.
   - 실제 연결된 SSID를 자동 탐지하고 선택값과 반드시 대조한다.
   - 다른 핫스팟을 선택/입력할 수는 있지만 “성공 검증 전 환경”임을 강하게 경고하고 명시적 재확인을 받으며, 메타데이터에 실제 SSID와 검증되지 않은 프로필임을 남긴다.
3. 수집 시간(분)
   - 양의 숫자만 허용하고 초로 정확히 변환한다.
   - RX 수집 시간은 입력 분 × 60초, TX는 RX보다 10초 길다.
4. 카메라 사용 여부
   - 먼저 V4L2 장치를 자동 탐지해 목록을 보여준다.
   - 카메라가 있다고 답하면 선택 장치를 실제 검사하고, 640x480 10 FPS 실시간 미리보기 창과 WebM 녹화를 동시에 사용한다.
   - 기존 `WebcamRecorder`의 기본 동작은 미리보기가 켜진 상태이므로 재사용하라. `--camera-no-preview`를 넘기지 말라.
   - 카메라가 없거나 사용하지 않는다고 답하면 `--camera-device`를 넘기지 않고 계속할 수 있지만, 라벨 검증 영상이 없다는 경고와 확인을 받고 메타데이터에 남긴다.

TX 터미널에서도 최소한 다음을 확인/입력하게 하라.

- 연결한 핫스팟 프로필(기본 `김민혁 핫스팟`)
- RX의 현재 IPv4 주소 또는 자동 검색으로 발견한 RX
- RX에서 정한 인원 수와 수집 시간(분)을 RX의 제어 메시지로 받아 화면에 표시하고 TX 운영자가 확인할 수 있게 한다.

수집 설정의 단일 진실 공급원은 RX wizard다. RX가 `num_people`, `duration_sec`, hotspot profile, camera policy, rate, size, data port, session ID를 확정해 handshake 뒤 TX로 보내고, TX 운영자는 같은 요약을 승인한다. TX에서 같은 값을 별도로 다시 입력해 독립적으로 결정하지 말라. 어떤 이유로 양쪽 값이 다르면 절대 시작하지 않는다. TX의 무선 인터페이스명도 RX 기준값 `wlp4s0`으로 고정하지 말고 현재 route/link에서 탐지하거나 옵션으로 받는다.

입력 단계마다 취소(`Q` 또는 Ctrl+C)가 가능해야 한다. 취소 시 CSI 로거, 카메라, 소켓 같은 자식 프로세스/자원을 정리하고 수집 데이터인 것처럼 보이는 불완전한 결과를 성공으로 표시하지 말라.

## 5. RX/TX 연결 확인 및 시작 동기화

단순히 두 터미널에 같은 명령을 보여주는 것으로 끝내지 말고, 실제 제어용 핸드셰이크를 구현하라. 데이터 UDP 포트 `5005`와 충돌하지 않는 별도 TCP 제어 포트를 사용하며, 포트 번호는 상수/옵션으로 명확히 정의하라. 로컬 핫스팟 내부에서만 사용하고 제어 메시지는 최대 크기를 제한한 versioned JSON Lines처럼 명시적인 형식으로 구현하라. 메시지에는 최소 `protocol_version`, `session_id`, 예측 불가능한 세션 nonce, message type을 포함하고 스키마를 검증하라. 모든 소켓에 timeout을 설정하며 retry, heartbeat, 중복 메시지의 idempotency를 정의하고 오류를 한국어로 설명하라. `eval`을 사용하지 말라.

필수 상태 순서는 다음과 같다.

```text
RX 실행 및 사전 점검
  -> RX 제어 포트 LISTENING
  -> RX 화면에 현재 Wi-Fi IPv4, 제어 포트, 일회용 연결 PIN 표시
  -> TX 실행 및 RX 주소 입력/발견
  -> TX가 IP/PIN으로 접속해 먼저 HELLO/TX_READY 신호 전송
  -> RX가 응답해 양방향 제어 연결 확인
  -> 양쪽의 실제 SSID, 로컬 IP, 역할, 프로토콜 버전, 인원 수, 시간 설정 대조
  -> TX에서 RX IP로 ping 4회 실행 및 결과 전송
  -> RX가 모든 검사 결과와 최종 설정 요약 표시
  -> RX에서만 "모든 준비가 완료되었습니다. 수집을 시작하려면 Y" 질문
  -> Y가 아니면 시작하지 않고 재확인 또는 안전 종료
  -> Y 입력 시 RX가 기존 수집 파이프라인을 준비하여 CSI logger/UDP receiver가 READY가 됨
  -> RX가 TX에 START 전송
  -> TX가 START_ACK를 회신
  -> TX가 START를 받은 뒤에만 safe_sender.py로 실제 UDP 송신 시작
  -> RX는 첫 UDP 패킷을 받은 시점부터 사용자가 정한 시간만큼 계측
  -> 양쪽이 완료/실패 상태를 교환하고 요약 출력
```

여기서 “TX가 먼저 신호를 보낸다”는 것은 **TX_READY 제어 신호가 먼저**라는 뜻이다. 실제 CSI용 UDP 트래픽은 반드시 RX의 CSI logger와 UDP receiver가 준비되고 RX 운영자가 `Y`를 누른 뒤 RX가 `START`를 보냈을 때 시작해야 한다. 이는 기존 성공 사례의 `READY 이후 송신` 조건을 보존하기 위한 필수 조건이다.

자동 discovery는 선택 사항이다. 기본 UX는 RX가 현재 주소/포트/일회용 PIN을 보여주고 TX가 이를 입력하는 확실한 방식으로 만들어라. PIN은 같은 핫스팟의 엉뚱한 장치가 실수로 붙는 것을 방지하는 세션 확인값이며 Wi-Fi 비밀번호가 아니다. 방화벽을 자동으로 끄거나 sudo로 규칙을 임의 변경하지 말고 필요한 포트 안내만 제공하라.

연결 검증은 최소한 다음을 포함해야 한다.

- RX/TX 모두 Wi-Fi에 연결돼 있는지 확인
- 두 PC의 실제 SSID와 현재 BSSID가 서로 같고 선택한 프로필과 같은지 확인
- 김민혁 핫스팟이면 실제 SSID가 정확히 `Minhyuck S24+`인지 확인
- RX/TX IPv4가 유효하며 loopback가 아닌지 확인
- TX에서 `ip route get <현재_RX_IP>` 결과가 Wi-Fi 인터페이스를 통하는지 확인
- TX에서 RX로 `ping -c 4` 성공 여부 확인
- 제어 채널 요청/응답으로 양방향 애플리케이션 수준 통신 확인
- 가능하면 주파수 2437 MHz/채널 6 확인. 불일치는 자동으로 바꾸지 말고 차단 또는 강한 경고 후 재확인
- RX에서 커널이 성공 기준인 `4.15.0-213-generic`인지, `connector_log=1`인지, 수정 CSI 도구/드라이버/펌웨어가 존재하고 실행 가능한지, RX MAC/인터페이스, 디스크 공간, 중복 `log_to_file` 없음, Wi-Fi power save 상태를 확인
- 카메라 사용 시 장치/포맷/GStreamer/미리보기 가능 여부 확인

연결 실패, SSID/BSSID 불일치, ping 실패, 제어 프로토콜 버전 불일치, TX/RX 설정 불일치는 기본적으로 수집을 차단하고 재시도/종료를 제공하라. 오래된 IP로 자동 fallback하지 말라. 제어 연결의 peer IP, TX가 보고한 로컬 IP, 실제 데이터 패킷 송신원 IP가 일치하는지도 확인하라. 방화벽이나 AP client isolation 가능성 등 다음 점검 명령도 안내하라.

## 6. 기존 수집 파이프라인과 통합

다음 성공 동작은 바꾸지 말라.

- CSI 수신은 `capture_prototype.py`를 중심으로 수행
- UDP 데이터 포트 `5005`
- 기본 송신률 100 packets/s
- 페이로드 512 bytes
- TX 송신 시간 = RX 수집 시간 + 10초
- RX 타이머는 첫 실제 UDP 데이터그램 수신 시 시작
- `sudo -v`를 수집 전에 수행하고 실제 로거는 비대화형 권한으로 실행
- 세션별 CSI, 영상, UDP 기록, runtime JSON, meta.json, 파싱 및 정형화 결과 생성
- 인원 수에 따라 `data/<N>_people/{CSI_DATA,Web_Cam,META_DATA}` 사용
- 카메라 사용 시 미리보기와 녹화 동시 수행

필요하면 `capture_prototype.py`에 작고 하위 호환되는 옵션/준비 완료 신호를 추가하라. 권장 방식은 기존 캡처 프로세스를 subprocess로 실행하고 stdout의 사람이 읽는 문구만 불안정하게 파싱하는 것보다, 명시적인 machine-readable READY 신호 또는 콜백/모듈 API를 제공하는 것이다. 단, 기존 CLI 호출은 계속 동작해야 한다.

현재 `UDPRecorder`는 포트 5005로 들어오는 아무 첫 패킷에도 타이머를 시작할 수 있다. 새 동기화 경로에서는 협상된 TX IP와 세션 nonce/magic을 가진 데이터 패킷만 해당 세션의 유효 트래픽으로 인정해 타이머를 시작하라. 이를 위해 `safe_sender.py`와 recorder에 하위 호환 옵션을 추가할 수 있다. 제3자의 우연한 UDP 패킷이나 오래된 sender가 새 세션을 시작시키면 안 된다.

RX에서 `Y`를 누르기 전에는 최종 수집을 시작하지 말라. 또한 `Y` 직후 TX에 START를 먼저 보내 버려 RX 로거가 준비되기 전에 UDP가 도착하는 race condition을 만들지 말라. RX의 로거와 UDP receiver가 실제 READY가 된 것을 확인한 후 START를 보내라. 준비 중 카메라 미리보기가 먼저 뜨는 것은 허용한다.

핫스팟 표시 이름, 실제 SSID, 실제 BSSID, 주파수/채널, RX/TX 현재 IP와 MAC, 연결 검사 결과, 카메라 사용 여부/장치/preview 여부, 요청 인원, 계획 시간, 핸드셰이크·승인·START 시각, sender 결과/전송 수, 중단 이유 및 최종 성공/실패를 가능한 범위에서 기존 `capture_runtime.json` 또는 별도 세션 제어 로그에 남겨라. nonce 자체는 로그에 꼭 필요하지 않으며 비밀정보는 제외한다. 스키마를 바꾸면 하위 호환성을 유지하고 문서화하라.

## 7. 안전성과 사용자 경험

- UI 문구는 한국어로 간결하고 단계 번호와 `[통과]`, `[경고]`, `[실패]`, `[대기]` 상태를 보여라.
- 비밀번호, sudo 입력, 민감한 네트워크 자격 증명을 로그에 저장하지 말라.
- 입력값을 shell 문자열로 조합해 `shell=True`로 실행하지 말라. subprocess 인자 배열을 사용하라.
- 사용자 입력으로 경로 traversal이나 임의 명령 실행이 가능하면 안 된다.
- 같은 실행기를 두 번 켰을 때 포트 충돌과 중복 로거를 이해하기 쉽게 알리고 새 수집을 막아라.
- TX가 끊기거나 sender가 비정상 종료하면 RX가 이를 감지하고 실패 상태를 기록하라.
- RX가 중단되면 TX sender도 종료하도록 제어 연결 또는 명시적 STOP 메시지를 사용하라.
- 수집 중 heartbeat, UDP packet stall, 카메라 및 logger 조기 종료를 감시하고 합리적인 timeout/실패 정책을 문서화하라.
- 정상/오류/Ctrl+C 모든 경로에서 자식 프로세스를 정리하라. 기존에 실행 중이던 사용자 프로세스를 PID 이름만으로 무차별 종료하지 말라.
- 네트워크 연결을 자동 변경하거나 저장된 Wi-Fi 프로필을 수정/삭제하지 말라.
- `.desktop` 파일의 실행 권한과 Trust 관련 Linux 데스크톱 제약을 설치 문서에 설명하라.
- 기존 데이터와 사용자의 다른 변경을 삭제하거나 덮어쓰지 말라.

## 8. 테스트와 검증

구현 후 반드시 직접 검증하라.

1. 변경한 Python 파일에 대해 문법 검사
2. 변경한 shell 파일에 대해 `bash -n`
3. 인원 수/분/카메라 선택 입력 검증 테스트
4. localhost에서 가짜 RX/TX를 사용한 핸드셰이크 테스트
5. 다음 상태 전이 테스트:
   - TX_READY 전에는 Y 승인 불가
   - RX 승인과 capture READY 전에는 UDP sender 시작 불가
   - 설정 불일치 시 차단
   - timeout/disconnect 시 양쪽 안전 종료
   - 정상 경로에서 sender duration이 capture duration보다 정확히 10초 김
   - 중복 START는 무시되며 다른 송신원/nonce의 UDP는 타이머를 시작하지 못함
   - 제어 연결 단절, sender/logger/camera 조기 종료, Ctrl+C에서 고아 프로세스 없이 실패 기록
6. 카메라 없음/사용 안 함 경로 테스트
7. `.desktop`의 `Exec`, `Path`, `Terminal=true` 및 대상 파일 존재 확인
8. 기존 `start_4_people_20min_capture.sh`와 `safe_sender.py` CLI의 하위 호환성 확인
9. 가능한 경우 3~5초 localhost mock 수집에서 100 packets/s, 512-byte 설정과 정상 COMPLETE 교환 확인

실제 CSI 하드웨어나 두 번째 PC가 없어 수행할 수 없는 검증은 성공했다고 꾸미지 말고 `미검증`으로 구분하며, 두 PC에서 실행할 정확한 수동 검증 절차를 제공하라.

## 9. 완료 조건

다음 조건을 모두 만족해야 완료다.

- RX와 TX 각각 바탕화면 버튼 하나로 한국어 터미널 실행기가 열린다.
- RX에서 인원 수, 김민혁 핫스팟 여부, 수집 분, 카메라 여부를 묻는다.
- 카메라 선택 시 실시간 화면과 녹화가 동시에 동작한다.
- 두 PC가 같은 현재 SSID에 있고 서로 통신 가능한지 수집 전에 검증한다.
- TX가 먼저 TX_READY 신호를 보내고, RX는 이를 확인한 뒤에만 최종 Y 질문을 표시한다.
- RX에서 Y를 누르지 않으면 수집이 시작되지 않는다.
- Y 이후에도 RX CSI logger/UDP receiver READY 전에 TX 데이터 송신이 시작되지 않는다.
- 동적 IP/BSSID를 현재 값에서 얻고 과거 값을 고정하지 않는다.
- 수집 시간과 인원 수가 출력 경로 및 메타데이터에 정확히 반영된다.
- 오류나 중단 시 양쪽이 명확한 원인과 복구 방법을 표시하고 자원을 정리한다.
- 자동 테스트가 통과하며 기존 성공 수집 명령도 깨지지 않는다.
